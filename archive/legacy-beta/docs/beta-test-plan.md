# 네이버 블로그 자동화 시스템 최적화 베타 테스트 방안

작성일: 2026-08-27
기준 시간대: Asia/Seoul
모드: 베타
파이프라인 버전: `workflow-optimized-v1`
상태: Phase 0~4 로컬 구현 완료, 현재 Gate 0의 Q3·신규 계약 증거 보완 및 대규모 실행 준비 대기
목표: 실제로 확보·동결한 주제 manifest를 사용해 콘텐츠 파이프라인의 성능·품질·재현성·운영 안정성을 측정. 주제 기간은 manifest가 증명하는 범위만 사용하며, 확보하지 못한 기간을 추정하지 않는다.

## 1. 결론

현재 시스템에 가장 합리적인 베타 테스트는 **500편을 한 번에 무작위 실행하는 방식이 아니라, 계약 전환 확인·Gate 0 폐쇄·반복 통제군·대표 주제군·부하 테스트를 순서대로 통과시키는 manifest 기반 단계적 테스트**다.

기본안은 다음과 같다.

| 구분 | 작업 수 | 목적 |
|---|---:|---|
| 계약 전환 calibration | 3개 작업 | `workflow-optimized-v1` 신규 로그·manifest·로컬 Gate 확인. 대규모 수에 포함하지 않음 |
| Gate 0 | 10개 작업 | 현재 10행 manifest의 로컬 산출물·Notion 저장 무결성·Q3 증거 폐쇄. 500편에 포함하지 않음 |
| 반복 통제군 | 45개 작업 | 같은 주제 15개를 각 3회 실행해 생성 변동성과 재현성 측정 |
| 대표 주제군 | 300개 작업 | 월·카테고리·검색 의도·난이도를 층화한 실제 성능 측정 |
| 부하 테스트 | 200개 작업 | 동시성·큐·외부 저장 병목 측정 |
| 대규모 합계 | 555개 작업 | 500개 고유 글 + 45개 반복 통제군 + 10개 Gate 0. calibration 3개는 별도 |

사용자가 “전체 실행 작업 수를 반드시 500개”로 제한하면 반복 통제군 45개를 포함해 **455개 고유 글 + 45개 반복 작업**으로 조정한다. 그러나 시스템 성능의 재현성까지 파악하려면 500개 고유 글 외에 반복 작업을 추가하는 편이 낫다.

베타에서는 네이버에 게시하지 않는다. 검수된 결과를 로컬 `final/`에 만들고, Q1과 canonical manifest 검증 직후 Notion 운영 데이터베이스에 `모드=베타`, `상태=테스트`로 저장해 파이프라인의 마지막 허용된 외부 쓰기까지 확인한다. 현재 로컬 runner와 외부 adapter는 Notion 쓰기를 자동 실행하지 않으므로, Notion 저장은 `notion-rider`의 직렬 연결 작업으로 별도 기록한다.

실행 준비 문서는 `evaluation-rubric.md`, `metrics-spec.md`, `beta-report-template.md`이며, 실제 주제 입력은 `manifests/beta-topic-manifest-template.csv`를 복사해 만든다. 사람은 Notion의 `베타 테스트 검수` 보기에서 글·이미지·품질·성능 판정을 확인한다.

## 2. 현재 시스템 진단

### 2.1 확인된 구성

현재 루트 지침과 품질 Gate는 다음 순서다.

```text
topic-selector
  → researcher
  → writer
  → image-maker
  → content-assembler + Q1/manifest
  → notion-rider
  → Q2 저장 무결성
  → Q3 사람 검수
```

각 단계는 이전 단계의 산출물을 입력으로 받고, 다음 파일을 결과로 사용한다.

| 단계 | 주요 출력 | 현재 확인된 통과 기준 |
|---|---|---|
| topic-selector | `research/topic-selection-[키워드].md` | 주제·검색 의도·확인일·근거 |
| researcher | `research/[키워드].md` | 채택 정보마다 원문 URL·확인일 |
| writer | `drafts/[키워드].md` | 리서치 기반 본문·`[IMAGE:]` 마커 |
| image-maker | `assets/[키워드]/`, `image-map.md` | 이미지 열림·본문 연결·순서 일치 |
| content-assembler | `final/[키워드].md`, `-naver-layout.md`, `-naver-copy.md`, workflow manifest | 마커만 치환·본문 보존·시각 계약·canonical digest 검증 |
| notion-rider | Notion 새 페이지 | 실제 스키마 확인·첨부 업로드·저장 후 재조회 |

현재 구현에는 `schemas/workflow-contract.schema.json`, `tools/workflow_verifier.py`, `tools/manifest.py`, `tools/gate.py`, `.codex/hooks.json`, 단일 실행 상태·lock·재개를 담당하는 `tools/automation_runner.py`가 있다. 이 구성은 로컬 실행 순서, 산출물 digest, 실패 단계 단축, 외부 쓰기 차단을 검증하지만, 주제 CSV를 읽어 500건을 자동 분배하거나 실제 Notion 쓰기를 수행하는 배치 실행기는 아니다.

2026-08-26 Gate 0 기록에는 `manifests/beta-gate0-2026-08-17-24-10.csv`의 10행이 있다. 그중 1행은 `selected_existing_run`이고 9행이 신규 실행이다. 실행 로그상 10건 모두 로컬 단계와 Q1 항목을 통과했고, 10건의 Notion 페이지 생성·재조회도 기록되어 있다. 다만 이 기록들은 새 `pipeline_version` 필드를 포함하지 않는 이전 형식이며, `notion_roundtrip_digest`와 Q3 사람 평가가 기록되지 않았다. 따라서 이 결과는 읽기 전용 기준선·마이그레이션 증거로만 사용하고 `workflow-optimized-v1` Gate 0 통과로 간주하지 않는다.

### 2.2 현재 시스템의 한계와 대량 실행 차단 조건

- 실제로 동결된 주제 manifest는 2026-08-17~24 범위의 10행뿐이며, 1~7월 500개 모집단은 확인되지 않았다. 현재 manifest의 10건을 전체 모집단이나 대표 표본으로 확대 해석하지 않는다.
- `manifests/beta-topic-manifest-template.csv`는 헤더만 있는 템플릿이다. 500개 고유 주제와 15개 반복 대상이 들어간 실제 manifest는 아직 없다.
- runner는 단일 `daily-generate` 실행의 상태·lock·재개·manifest를 관리하고, `notion-rider`와 `naver-rider` 외부 호출은 건너뛴다. `external_adapter`도 현재는 Gate를 확인하는 dry-run만 허용한다. 따라서 CLI 한 번으로 500건의 전체 파이프라인 또는 Notion 저장이 완료되지 않는다.
- `launchd` 등록 파일은 존재하지만 현재 모두 `Disabled=true`이고 dry-run 인자를 사용한다. 스케줄러 파일의 존재를 대량 실행이나 외부 저장 가능성으로 세지 않는다.
- 기존 베타 JSONL은 `pipeline_version`이 없는 레거시 형식이다. 새 Schema 검증에 그대로 통과하지 않으므로 원본을 수정하지 않고, 호환 집계·기준선으로만 읽는다. 신규 실행은 반드시 `workflow-optimized-v1` 이벤트를 새 로그에 기록한다.
- 현재 기준선에서 Q3 사람 이미지 점수와 `notion_roundtrip_digest`는 측정되지 않았다. Notion 페이지 재조회 기록이 있더라도 Q2와 Q3의 완료 증거로 대체하지 않는다.
- Notion 대상은 `네이버 블로그 자동화 운영` 데이터 소스 `d4f6d9a1-e438-4c05-ae18-8558277c5d00`로 고정하지만, 매 실행 전 실제 연결·스키마·권한을 다시 조회해야 한다.

따라서 현재 다음 단계는 500건 실행이 아니라 **레거시 Gate 0의 Q2 round-trip 보완 → 신규 v1 calibration → 실제 모집단 manifest 동결 → 배치 운영 표면 확보**다. Q3 기록은 선택적 품질 분석으로 별도 보존한다.

## 3. 실험 설계 원칙

### 3.1 주제 모집단을 먼저 동결한다

실험 시작 전에 `topic_date`의 의미를 고정한다. 기본 정의는 **주제 또는 원문 자료가 확인된 날짜**이며, 실행일과 분리한다.

각 주제에는 최소한 다음 필드를 기록한다.

```yaml
topic_id: "2026-01-001"
topic: "..."
topic_date: "2026-01-15"
month: 1
category: "..."
search_intent: "정보 확인형"
difficulty: "중"
freshness_required: true
official_source_required: true
expected_input_tokens: null
expected_output_chars: null
selection_source_url: "..."
selected_at: "2026-08-25T...+09:00"
sampling_seed: "..."
```

후보 목록을 요청한 기간·카테고리 전체에 대해 확보하지 못하면 해당 범위를 임의로 채우지 않고 `topic-universe-blocked`로 중단한다. 현재 Gate 0의 2026-08-17~24 manifest는 해당 범위의 검증 표본일 뿐이며, 1~7월의 검색량이나 주제 분포로 환산하지 않는다. 1~7월을 계속 목표로 삼으려면 그 기간의 원문 URL과 `topic_date`가 있는 새 manifest를 별도로 동결한다.

### 3.2 완전 무작위가 아니라 층화 무작위로 추출한다

주제는 다음 순서로 뽑는다.

1. 실제 manifest에 기록된 날짜 범위와 월을 1차 블록으로 둔다.
2. 각 블록 안에서 카테고리와 검색 의도별 최소 표본을 확보한다.
3. 난이도와 최신성 필요 여부를 균형 있게 배치한다.
4. 같은 블록 안에서 고정 seed로 무작위 추출한다.
5. 실행 순서는 다시 무작위화한다.

카테고리 목록이 사전에 정해져 있지 않으면 후보 모집단을 먼저 분류하고, 분류 결과와 분류 규칙을 manifest에 보존한다. 카테고리별 5개만으로 세밀한 우열을 주장하지 않고, 전체 성능과 큰 차이 탐지에 사용한다.

### 3.3 같은 주제 반복으로 재현성을 측정한다

LLM은 같은 입력 조건에서도 항상 동일한 결과를 보장하지 않는다. 따라서 대표적인 쉬움·보통·어려움 주제 각 5개, 총 15개를 선정하고 각 3회 실행한다. 현재 시스템이 실제로 전달·기록하지 못하는 모델 옵션은 고정했다고 간주하지 않으며, 이미지 생성에는 지원되지 않는 seed를 재현성 근거로 사용하지 않는다.

반복군에서는 다음을 고정한다.

- 모델·프롬프트·가이드 파일 버전과 `pipeline_version`
- 실제로 전달된 출력 제한·생성 옵션
- 실행 환경과 시간대
- 이미지 생성 옵션
- Notion 저장 방식

반복 결과는 품질 비교보다 실행 시간·실패 여부·출력 길이·출처 수·이미지 수의 변동을 확인하는 데 우선 사용한다.

## 4. 단계별 베타 실행안

### Gate -1: `workflow-optimized-v1` calibration 3개

기존 10건을 새 로그로 덮어쓰지 않고, 새 `batch_id`·`run_id`를 사용하는 3개 주제로 외부 저장 없는 calibration을 수행한다. 세 작업 모두 다음을 확인해야 한다.

- `pipeline_version=workflow-optimized-v1`인 stage·manifest 기록
- 세 최종 Markdown, `image-map.md`, 본문 이미지, 썸네일의 canonical digest
- 실패 단계 이후 하위 단계가 실행되지 않는지
- `daily-generate --dry-run`과 `verify-manifest`가 실제 입력을 검증하는지
- Notion·네이버 외부 호출이 발생하지 않는지

이 calibration은 대규모 작업 수에 포함하지 않는다. 기존 10건을 재사용하려면 사용자가 재베타·비교를 명시하고 새 실행 식별자를 발급해야 한다.

### Gate 0: 현재 10행 표본의 폐쇄

현재 대상은 `manifests/beta-gate0-2026-08-17-24-10.csv`다. 10행 중 1행은 기존 실행 참조이고 9행만 신규 실행이므로, 신규 생성·저장 건수는 9건으로 따로 집계한다. 이 10건은 2026-08-17~24의 검증 표본이며 500개 모집단을 대신하지 않는다.

기존 기록에서 로컬 단계와 Notion 페이지 재조회는 모두 기록되어 있지만, 레거시 로그이므로 다음 보완 없이는 Gate 0을 통과시키지 않는다.

- 기존 산출물·페이지를 덮어쓰지 않고 Q3 사람 검수와 모바일 이미지 평가는 선택적으로 기록한다.
- `notion_roundtrip_digest`, `storage_integrity`, 페이지·첨부 순서를 새 형식으로 기록한다.
- 레거시 로그는 보존하고, 같은 결과를 `workflow-optimized-v1` 신규 실행으로 증명할 경우 새 run을 만든다.
- Q1·Q2를 통과한 뒤 이 표본을 calibration 완료로 보고한다. Q3 결과는 별도 참고 기록으로 남긴다.

Gate 0에서 다음 중 하나라도 발생하면 대량 테스트를 시작하지 않는다.

- 잘못된 Notion 데이터베이스 또는 데이터 소스에 쓰기
- 기존 파일 또는 기존 Notion 항목 덮어쓰기
- 본문과 이미지 순서 불일치 또는 Q2 round-trip digest 누락
- 이미지 업로드 후 페이지 재조회 실패
- 출처 없는 사실·허위 공식 화면·권리 불명 자산이 통과
- 실패 단계 이후 다음 단계가 계속 실행됨

### Gate 1: 45개 반복 통제군

Gate -1과 Gate 0이 닫힌 뒤 15개 주제를 3회씩 실행한다. 이 단계는 새 시스템의 재현성과 지연 변동을 확인하는 목적이며, 각 작업은 새 `workflow-optimized-v1` 로그와 독립된 최종 파일·manifest를 가진다.

산출물:

- 주제별 3회 결과
- 단계별 지연시간 분포
- 성공·실패·재시도 기록
- 결과 해시와 입력 가이드 버전
- 동일 주제의 품질·길이·이미지 수 변동

### Gate 2: 300개 대표 주제군

Gate 1이 통과한 뒤, 실제 확보된 주제 모집단의 월·카테고리·검색 의도·난이도를 기준으로 균형 있게 배분한다. 특정 월별 최소 건수를 미리 채우지 않으며, 후보가 부족하면 실제 확보 수와 불확실성을 보고한다. 현재 10행 표본만으로 300개를 채우지 않는다.

이 단계의 목적은 “어떤 주제가 좋은가”보다 다음을 측정하는 것이다.

- 주제 난이도에 따른 단계별 시간 변화
- 최신성·공식 출처 요구가 실패율에 미치는 영향
- 이미지가 많은 글의 조립·Notion 업로드 병목
- 월별·카테고리별 품질 편차
- 단일 글 평균이 아닌 P50·P95·P99 성능

### Gate 3: 200개 부하 테스트

대표 주제군과 다른 200개의 작업을 사용해 로컬 생성·계약 검증 구간의 동시성을 단계적으로 높인다. 현재 runner에는 CSV 배치 분배 기능이 없으므로, 배치 coordinator 또는 동일한 단일 작성자 운영 절차를 먼저 마련하고 실행 목록을 고정한다.

```text
동시성 1 → 2 → 4 → 8 → 16
```

각 수준에서 작업 수를 동일하게 배분하고, 다음 구간을 찾는다. Notion 페이지 생성·첨부·재조회는 베타 규칙상 직렬로 유지하므로 동시성 sweep에 섞지 않는다.

- 처리량이 증가하는 구간
- 처리량이 포화되는 구간
- 큐 대기시간이 급증하는 구간
- 외부 API 429·인증·업로드 오류가 증가하는 구간
- Notion 저장이 병목이 되는 구간

부하 테스트에서 글 생성·이미지·조립과 외부 쓰기를 분리해 측정한다. 현재 외부 adapter는 dry-run만 지원하므로, 실제 Notion 처리량은 Q1과 manifest 검증을 통과한 직렬 `notion-rider` 작업의 별도 측정값으로 기록한다. 로컬 생성 병목인지, 이미지 업로드 병목인지, Notion 페이지 생성 병목인지 구분하지 못하면 최적화 방향을 결정할 수 없다.

## 5. 측정 항목

### 5.1 성능

| 영역 | 측정값 |
|---|---|
| 단계 시간 | topic-selector·researcher·writer·image-maker·content-assembler·notion-rider의 시작·종료 시각 |
| 로컬 처리시간 | 첫 로컬 단계부터 manifest 검증 완료까지. Notion 외부 쓰기와 분리 |
| 전체 처리시간 | 첫 단계 시작부터 Notion Q2 재조회 완료까지. Q2가 없으면 미측정 |
| 지연 분포 | 평균, P50, P95, P99, 최대값 |
| 처리량 | 시간당 완료 작업 수, 동시성별 완료 작업 수 |
| 대기 | 큐 대기, API 응답 대기, 이미지 업로드 대기 |
| 비용 | 입력·출력 토큰, 이미지 생성 수, 외부 API 비용, 작업당 비용 |
| 안정성 | 실패율, 재시도율, 중단율, 중복 실행 수 |

현재 `tools.automation_runner`의 `daily-generate`는 콘텐츠 생산자를 호출하지 않고 기존 로컬 산출물과 manifest만 검증한다. 생산자를 호출하지 않은 단계는 `skipped`, manifest만 확인한 `content-assembler`는 `validated`, 실행 전체는 `local-only`로 기록한다. 따라서 `passed`는 실제 단계 실행과 검수를 통과한 경우에만 사용하며, `local-only`를 전체 베타 성공이나 Notion 저장 성공으로 집계하지 않는다. 토큰·비용·Q2 digest를 측정하지 못한 작업은 추정값으로 채우지 않고 `미측정`으로 보고한다.

### 5.2 품질

| 영역 | 통과 기준 |
|---|---|
| 리서치 | 채택 사실마다 원문 URL과 확인일이 있음 |
| 본문 | 리서치·스타일·SEO 가이드와 일치하고 출처 밖 핵심 주장이 없음 |
| 이미지 | 실제로 열리고 본문 목적·순서와 일치함 |
| 조립 | 이미지 마커 수와 이미지 수가 일치하고 마커 치환 외 본문이 동일함 |
| Notion | 본문 구조·링크·이미지 순서가 유지되고 저장 후 재조회됨 |
| 중복 | 주제 중복·파일명 충돌·이미지 해시 중복이 없음 |
| 안전 | 권리 불명 이미지, 가짜 공식 화면, 개인정보·비밀값이 없음 |

### 5.3 사람 평가와 자동 평가

대규모 500개 작업 전체는 규칙 기반 검사를 수행하고, 다음을 별도 표본으로 사람 평가할 수 있다. 사람 평가와 Q3 기록은 calibration 또는 다음 단계의 필수 차단 조건이 아니다.

- 100개: 구조·문체·SEO·검색 의도 충족 여부
- 50개: 출처 대조를 포함한 사실성·유용성 블라인드 평가
- 20개: 이미지와 본문 연결, 정보 전달성, 권리 위험 평가

LLM 평가자는 보조 지표로만 사용한다. 사람이 작성한 기준 샘플과 AI 생성 샘플을 섞어 평가자에게 제시하고, 평가자가 생성문을 선호하는 편향이 있는지 확인한다.

## 6. 성공·경고·중단 기준

### 즉시 중단

- 잘못된 Notion 데이터베이스 또는 잘못된 데이터 소스에 저장
- 기존 정식 자료·기존 Notion 항목의 수정·삭제·덮어쓰기
- 외부 쓰기 응답이 불명확한데 재전송해 중복 페이지 생성
- 출처가 없는 최신 수치·정책·가격이 본문에 포함
- 공식 화면이 필요한 위치에 허위 생성 화면 사용
- 이미지·본문·Notion 순서가 달라짐
- 인증 토큰·쿠키·개인정보가 파일이나 로그에 기록됨

### Gate 통과 기준

- 새 실행 이벤트의 `workflow-optimized-v1` Schema 검증 100%
- Gate 0의 로컬 Q1 통과 및 canonical manifest 검증 100%
- Gate 1 이후 로컬 산출물 통과율 95% 이상
- 채택된 글의 출처·조립·이미지 검증 100%
- Notion 저장을 시도한 글의 Q2 저장 후 재조회·round-trip digest 일치율 100%
- 선택적 사람 검수 표본의 결과는 별도 보고하며 Gate 통과 필수 조건으로 사용하지 않음
- 중복 파일·중복 페이지·본문 변형 0건
- 모든 실패 작업에 단계·오류 분류·다음 조치가 기록됨
- 부하 증가에 따라 P95 지연과 오류율이 함께 보고됨

절대적인 처리시간 목표는 새 v1 calibration 기준선이 나오기 전에 임의로 정하지 않는다. Gate 1의 기준선 대비 대표 주제군 P95가 1.5배를 넘거나, 부하 테스트에서 처리량 증가 없이 P95만 급증하면 병목 원인을 확인한 뒤 다음 단계로 진행한다. 레거시 로그의 시간은 v1 기준선과 직접 비교하지 않는다.

## 7. 저장·격리·재개 규칙

### 7.1 로컬 파일

현재 `research/`, `drafts/`, `assets/`, `final/` 경로 규칙은 보존한다. 다만 배치 실행 중에는 각 주제의 파일명 충돌을 방지하기 위해 manifest에 `topic_id`와 대표 키워드를 함께 기록한다.

기존 `추석-기차표-예매` 산출물은 읽기 전용 기준 샘플로 취급하고, 베타 실행에서 덮어쓰지 않는다. 같은 키워드가 다시 선택되면 새 실행을 만들지 않고 중복으로 보류한다.

### 7.2 실행 기록

각 작업에 다음 실행 메타데이터를 남긴다.

```yaml
event_type: "stage"
batch_id: "beta-2026-08-27-01"
run_id: "RUN-20260827-0001"
topic_id: "TOPIC-..."
stage: "content-assembler"
pipeline_version: "workflow-optimized-v1"
started_at: "...+09:00"
ended_at: "...+09:00"
status: "passed"
attempt: 1
artifacts: []
error_type: null
error_message_safe: null
```

단계별 상태는 `pending → running → passed` 또는 `failed`, `blocked`로 제한한다. `failed`와 `blocked`는 자동으로 다음 단계에 전달하지 않는다.

runner 상태는 `.automation/state/<run_id>.json`, 실행 로그는 `.automation/logs/<run_id>.jsonl` 또는 실행별 `runs/<run_id>.jsonl`에 둔다. 실행 경로를 선택하더라도 새 이벤트의 필수 필드와 단일 작성자 원칙은 동일하게 적용한다. 기존 레거시 로그는 수정하거나 새 버전으로 덧씌우지 않는다.

### 7.3 Notion

Notion 저장 전 다음 순서를 고정한다.

```text
데이터 소스 조회
→ 실제 스키마 대조
→ 같은 날짜·모드의 차수 조회
→ 최종 파일·이미지 검수
→ Q1·manifest 재검증
→ 이미지 파일 업로드
→ 페이지 생성
→ 생성 페이지 재조회
→ Q2 round-trip digest 기록
```

각 베타 글은 `notion-config.md`의 속성을 사용하고 `모드=베타`, `상태=테스트`, `검수 결과=대기`로 시작한다. 저장 성공만으로 품질 통과로 표시하지 않는다. 본문·이미지 재조회와 Q2 digest 기록까지 끝난 뒤에도 Q3 사람 검수가 남아 있으면 `사람 검수=대기`를 유지한다. 산출물이 바뀌면 기존 manifest를 재사용하지 않고 다시 생성·검증한다.

현재 runner와 외부 adapter는 외부 쓰기를 실행하지 않는다. 따라서 실제 Notion 저장은 Q1과 manifest 검증을 통과한 `notion-rider`의 직렬 연결 작업으로 수행하고, 그 결과를 동일한 `run_id`의 로그에 남긴다. CLI·launchd·dry-run 성공은 Notion 저장 성공으로 집계하지 않는다.

## 8. 결과 분석

최종 보고서는 전체 평균 하나가 아니라 다음 표를 포함한다.

1. 전체 성공률과 95% 신뢰구간
2. 단계별 성공률·실패율·재시도율
3. 단계별 평균·P50·P95·P99 시간
4. 월·카테고리·검색 의도·난이도별 성능
5. 이미지 수와 본문 길이에 따른 성능 변화
6. 동시성별 처리량·큐 대기·오류율
7. Notion 저장 성공·재조회 성공·중복 여부
8. 사람 평가와 자동 평가의 차이
9. 반복 통제군의 실행 간 변동성
10. 다음 배치에서 수정할 병목과 수정 우선순위

현재 체크포인트는 다음처럼 별도 보고한다.

| 항목 | 2026-08-26 기록 | 판정 |
|---|---:|---|
| Gate 0 manifest 행 | 10 | 1개 기존 참조, 9개 신규 |
| 로컬 단계·Q1 기록 | 10/10 | 레거시 호환 증거 |
| Notion 페이지 생성·재조회 기록 | 10/10 | Q2 digest 미기록 |
| Q3 사람·모바일 이미지 평가 | 0/10 | 미측정 |
| `workflow-optimized-v1` 신규 이벤트 | 0/10 | 새 calibration 필요 |

이 표는 `baseline/phase0-2026-08-26.json`의 읽기 전용 기준선과 기존 JSONL에서 산출한 체크포인트다. 500개 전체 성공률은 새 v1 로그와 Q2·Q3 증거가 쌓인 뒤에만 계산한다. 월별·카테고리별 표본이 작으면 해당 그룹의 수치를 정밀한 순위로 해석하지 않고 탐색적 결과로 표시한다.

## 9. 최종 운영 판정

베타 결과에 따라 다음 세 가지 중 하나로 판정한다.

### 통과

새 v1 계약·Q1·Q2가 닫히고, 중대한 데이터·권리·출처·중복 오류가 없으며, 단계별 성능과 부하 한계가 기록되고, 재현성 있는 재실행이 가능하다. Q3 기록은 선택적으로 보존하며, 그때 소규모 정식 실행 여부를 별도로 결정한다.

### 조건부 통과

콘텐츠·저장 무결성은 통과하지만 특정 단계의 P95, 이미지 처리량, Notion 직렬 저장 또는 특정 주제군 실패율이 높다. 해당 병목을 개선한 뒤 같은 manifest 블록만 새 run으로 재검증한다.

### 실패

잘못된 외부 저장, 본문 변형, 출처 누락, 이미지 순서 오류, 중복 페이지, 인증 정보 노출이 발생하거나 실패 원인을 추적할 수 없다. 대량 실행을 중지하고 원인 단계부터 재설계한다. Q1·Q2 또는 v1 기록이 빠진 상태는 통과가 아니라 `대기`다.

## 10. 수정된 실행 순서

1. **기존 증거 보존**: `baseline/phase0-2026-08-26.json`과 기존 `runs/*.jsonl`을 읽기 전용으로 보존한다. 레거시 로그에 `pipeline_version`을 덧붙이거나 상태·해시를 수정하지 않는다.
2. **현재 Gate 0 폐쇄**: 2026-08-17~24 10행 표본의 기존 페이지를 덮어쓰지 않고 Q2 round-trip digest 증거를 보완한다. Q3 사람·모바일 평가는 선택적으로 기록하며, 이미 저장된 10건을 새 v1 성공으로 소급하지 않는다.
3. **v1 calibration**: 새 주제 3개를 선정해 외부 저장 없이 실행한다. 각 작업에서 `workflow-optimized-v1` 이벤트, manifest, Q1, 실패 단축을 검증하고 `validate-schema`·`verify-manifest`를 통과시킨다.
4. **실제 모집단 동결**: 500개 고유 주제와 15개 반복 대상에 대해 원문 URL, `topic_date`, `duplicate_key`, 검색 의도, 난이도, 샘플링 규칙을 채운 새 manifest를 만든다. 1~7월을 목표로 할 경우 그 기간의 실제 자료를 별도로 확보한다.
5. **배치 실행 표면 확보**: 현재 runner의 단일 실행 한계를 인정하고, CSV 행을 새 `run_id`로 분배·수집하는 coordinator 또는 동일한 직렬 운영 절차를 정한다. `launchd`는 비활성·dry-run 상태이므로 대량 실행기에 사용하지 않는다.
6. **Gate 1 반복군**: 15개 주제를 3회씩 실행하고 로컬 처리시간, 실패·재시도, 출력·이미지 변동을 기록한다. Notion 저장은 Q1·manifest 검증을 통과한 직렬 작업으로 분리한다.
7. **Gate 2 대표군**: 실제 모집단을 층화 추출한 300개를 실행한다. 새 v1 로그와 Q1·Q2를 모두 확보하고, Q3 표본 평가는 선택적으로 진행한다.
8. **Gate 3 부하군**: 별도 200개로 로컬 동시성만 `1 → 2 → 4 → 8 → 16` 순서로 시험한다. 이미지 실제 생성은 직렬 유지 조건을 지키고, Notion 페이지 생성·첨부·재조회는 항상 직렬로 측정한다.
9. **결과 판정**: `beta-report-template.md`에 단계별 P50/P95/P99, Q1·Q2 및 선택적 Q3, 중복·누락·비용·복구 결과를 집계한다. 미측정 값은 채우지 않는다.
10. **범위 고정**: 베타 전체에서 `naver-rider`, 네이버 로그인·임시저장·발행은 호출하지 않는다. 정식 전환은 Q1·Q2·대상·digest 검증과 임시저장 직전 사용자 확인을 적용한다.

위 순서가 준비되지 않은 상태에서는 500개 고유 글 또는 555개 대규모 작업을 시작하지 않는다.

## 11. 근거 자료

- [Holistic Evaluation of Language Models](https://arxiv.org/abs/2211.09110): 시나리오 분류, 표준 조건, 다중 지표, 원본 결과 공개.
- [Towards Reproducible LLM Evaluation](https://arxiv.org/abs/2410.03492): LLM 출력 변동성, 반복 실행, 불확실성 구간.
- [MLPerf Endpoints](https://mlcommons.org/benchmarks/endpoints/): 실제 엔드포인트, 부하 스윕, 재현성, 검토와 감사.
- [NVIDIA LLM Benchmarking Parameters](https://docs.nvidia.com/nim/benchmarking/llm/latest/parameters.html): 동시성, 큐, 처리량 포화, 지연시간 측정.
- [NIST Randomized Block Designs](https://www.itl.nist.gov/div898/handbook/pri/section3/pri332.htm): 블록화와 무작위화 원칙.
- [G-Eval](https://arxiv.org/abs/2303.16634): LLM 기반 품질 평가의 활용과 생성문 선호 편향 주의.
